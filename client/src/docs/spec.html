ТЗ: Разработка веб-сервиса подачи внутренних заявок в отдел снабжения

1. Цель проекта

Разработать веб-сервис, через который сотрудники организации подают заявки на закупку (канцелярия, оборудование, расходные материалы, услуги), а отдел снабжения принимает их, меняет статусы и оставляет комментарии. Сейчас заявки ходят по почте и мессенджерам и теряются; сайт собирает всё в одном месте и показывает, на каком этапе каждая заявка.

Критерии успеха: сотрудник подаёт заявку менее чем за 2 минуты; любая заявка видна в очереди снабжения сразу после отправки; сотрудник в любой момент видит статус и комментарий; ни одна заявка не теряется.

Реализация: монорепозиторий procurement/ — server/ (Node.js + Express + PostgreSQL) и client/ (React + Vite). Исходный статический прототип сохранён в prototype/zayavki.html как образец интерфейса.

2. Стек

  • Frontend: React (Vite), React Router
  • Backend: Node.js + Express
  • База данных: PostgreSQL
  • Авторизация: JWT, пароли хранятся в виде хеша (bcrypt)
  • Формат обмена: JSON, REST API
  • Валидация входных данных на сервере (например, zod или joi), параметризованные SQL-запросы

3. Роли пользователей

РольЧто может
Сотрудник (employee)Регистрируется и входит; создаёт заявку; видит только свои заявки; редактирует и отменяет заявку, пока она в статусе «Новая»; видит комментарий снабжения и историю статусов
Снабжение (buyer)Видит все заявки; фильтрует и ищет; меняет статус по разрешённым переходам; пишет комментарий сотруднику; срочные заявки показываются первыми; видит статистику и выгружает CSV
Администратор (admin)Всё, что умеет снабжение, плюс: управляет пользователями (назначает роли), справочниками подразделений и категорий

4. Функции

MVP — обязательно

  1. Регистрация и вход (email + пароль), выход
  2. Создание заявки: категория, срочность, дата «нужно к», ориентировочная сумма, обоснование, одна или несколько позиций (название, количество, единица)
  3. Список «Мои заявки» для сотрудника с фильтром по статусу
  4. Просмотр одной заявки целиком
  5. Очередь снабжения: все заявки, фильтр по статусу, срочные сверху
  6. Смена статуса заявки снабжением по допустимым переходам (см. п. 8)
  7. Комментарий снабжения к заявке, который видит сотрудник; при отклонении комментарий (причина) обязателен
  8. Редактирование и отмена своей заявки, пока статус «Новая»
  9. Разграничение доступа по ролям (сотрудник не видит чужие заявки, не меняет статусы)
  10. Админ-раздел: список пользователей и назначение роли
  11. Поиск по номеру заявки, автору, названию позиции и обоснованию
  12. История смены статусов в карточке заявки (кто, когда, из какого статуса в какой)

Если останется время

  • Экспорт списка заявок в CSV (в прототипе уже есть)
  • Простая статистика: всего, в работе, срочные, выполнено (в прототипе уже есть)
  • Email-уведомления о смене статуса
  • Прикрепление файлов (счёт, фото)
  • Пагинация списков (по 20 заявок)
  • Тёмная тема (в прототипе уже есть)

Не делаем

Онлайн-оплату, мобильное приложение, интеграции с внешними сервисами (1С, банки), многоступенчатое согласование с несколькими руководителями.

6. Таблицы базы данных

departments — подразделения

  • id (PK), name (уникальное)

categories — категории закупок

  • id (PK), name (уникальное)

users — пользователи

  • id (PK), full_name, email (уникальный, хранится в нижнем регистре), password_hash, role (employee | buyer | admin), department_id (FK → departments), created_at

requests — заявки

  • id (PK, нумерация с 1001), author_id (FK → users), category_id (FK → categories), is_urgent (boolean), due_date (date, может быть пустой), budget (numeric, может быть пустой, ≥ 0), justification (text, обязателен), status (new | review | buying | done | rejected | cancelled), buyer_comment (text), created_at, updated_at

request_items — позиции заявки

  • id (PK), request_id (FK → requests, удаляется вместе с заявкой), name, quantity (целое > 0), unit (по умолчанию «шт.»)

status_history — история статусов

  • id (PK), request_id (FK), old_status, new_status, changed_by (FK → users), changed_at. Запись создаётся при создании заявки и при каждой смене статуса в одной транзакции с изменением заявки.

Связи: подразделение 1—N пользователи; пользователь 1—N заявки; категория 1—N заявки; заявка 1—N позиции; заявка 1—N записи истории.

Индексы: requests(author_id), requests(status), request_items(request_id), status_history(request_id).

Пример создания заявки:

POST /api/requests
{
  "category_id": 2,
  "is_urgent": true,
  "due_date": "2026-11-25",
  "budget": 48000,
  "justification": "Вышел из строя монитор у оператора склада",

→ 201 { "id": 1044, "status": "new", ... }

Ошибки: 400 — неверные данные (в теле список полей с причинами), 401 — нет входа, 403 — нет прав, 404 — не найдено, 409 — недопустимый переход статуса или заявку уже нельзя менять.

8. Правила и ограничения

  • Допустимые переходы статусов: new → review → buying → done; из new, review, buying можно уйти в rejected; cancelled ставит только владелец из new. Из done, rejected, cancelled переходов нет. Пропускать этапы нельзя.
  • При отклонении комментарий снабжения обязателен.
  • В заявке минимум одна позиция; количество — целое число больше 0; обоснование обязательно; сумма не меньше 0; дата «нужно к» не в прошлом.
  • Сотрудник не может менять статус, роль или чужие заявки — проверка на сервере, а не только в интерфейсе. Чужая заявка для сотрудника отвечает 404.
  • Пароль минимум 8 символов, хранится только как bcrypt-хеш; сообщение об ошибке входа не говорит, что именно неверно (email или пароль).
  • Регистрация всегда создаёт роль employee; первый администратор создаётся скриптом начального заполнения.
  • Весь пользовательский текст экранируется при выводе (защита от XSS).
  • Интерфейс на русском, адаптивный (работает с телефона), доступный: подписи у полей, видимый фокус, контраст не ниже AA.
  • Просроченной считается заявка, у которой дата «нужно к» прошла, а статус не done, rejected, cancelled; в списке она помечается.

9. Приёмка (чек-лист)

  1. Сотрудник регистрируется, входит, создаёт заявку с двумя позициями — она появляется в его списке со статусом «Новая».
  2. Другой сотрудник не видит эту заявку; прямой запрос /api/requests/:id возвращает 404.
  3. Снабжение видит заявку в очереди, переводит её «Новая → На согласовании → В закупке → Выполнена»; в карточке видна история с датами и именами.
  4. Перевод «Новая → Выполнена» отклоняется сервером (409).
  5. Отклонение без комментария не проходит.
  6. Сотрудник редактирует и отменяет заявку в статусе «Новая», после смены статуса — не может.
  7. Сотрудник не может сменить статус через API (403).
  8. Админ назначает пользователю роль buyer, и у того появляется очередь.
  9. Сайт корректно работает на экране 360 px.

  1. Каркас проекта, подключение PostgreSQL, миграции таблиц и начальные данные (справочники, первый админ)

  3. CRUD заявок для сотрудника, история статусов
  4. Очередь снабжения, смена статусов по правилам, комментарии, поиск
  5. Админ-раздел
  6. Статистика и экспорт CSV
  7. Стили по прототипу, проверка на телефоне
  8. Прохождение чек-листа приёмки
